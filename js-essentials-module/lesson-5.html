5.1 Waiting without freezing

Everyday analogy · the fast-food counter

Synchronous (blocking): the cashier takes your order, then stands at the grill until your burger is cooked, and only then serves the next person. The line does not move.

Asynchronous (non-blocking): the cashier takes your order, hands you a number, and immediately serves the next customer. When your food is ready, your number is called and you pick it up.

JavaScript in the browser has one main thread — one cashier. If it stood and waited for a slow server, buttons would stop working and the page would freeze. So for slow jobs (network requests, timers, reading files, database queries) JavaScript works asynchronously: it starts the job, keeps going, and handles the result later.

If you think in Java

In Java you might start a new Thread to avoid blocking. JavaScript does not make you manage threads. Instead, the runtime (browser or Node.js) does the slow work in the background and puts your callback in a queue — the event loop — to run when the main thread is free.

5.2 Seeing it happen: setTimeout

setTimeout(callback, ms) runs a function after a delay. Before you press Run, predict the order of the four lines.

Why does "Drinks ready" print after "Serve next customer", even with a delay of 0 ms?

Because a timer's callback never interrupts code that is already running. It waits in the queue until the current script finishes. So all the normal, synchronous lines run first, then the waiting callbacks run in order of readiness. This is the event loop at work.

5.3 Callbacks, and why they get messy

The oldest way to handle "do this when it is done" is a callback. It works, but when one step depends on another, callbacks nest deeper and deeper. Programmers call this callback hell (or the "pyramid of doom").

Promises and async/await were added to JavaScript to fix exactly this.

5.4 Promises

A Promise is an object that stands for a value that is not ready yet — like the number on your fast-food receipt. A Promise is always in one of three states:

pendingstill working
→
fulfilledsuccess — here is the value
rejectedfailed — here is the error

You attach .then(callback) for success and .catch(callback) for failure. Below, getGrade pretends to be a slow server.

In real work you rarely create Promises with new Promise — functions like fetch() create them for you. Your job is mostly to use them.

5.5 async / await: asynchronous code that reads like normal code

Inside a function marked async, you can write await in front of a Promise. JavaScript pauses that function until the Promise settles, then gives you the value — while the rest of the page keeps running. Errors are handled with ordinary try / catch, just like Java.

  • line 11 async marks a function that can use await. An async function always returns a Promise.
  • line 14 await unwraps the Promise: record is the actual object, not a Promise.
  • line 16 If the Promise is rejected, await throws, and catch handles it.
  • line 23 Here we can use await at the top because this box runs your code inside an async function. In a normal script file, wrap it in an async function as on line 11.

5.7 Doing several things at once: Promise.all

If two requests do not depend on each other, do not wait for one before starting the other. Start both, then wait for all of them.

Summary

  • Slow jobs (network, timers, databases) are asynchronous: JavaScript starts them and continues, so the page never freezes.
  • A Promise is pending, then fulfilled or rejected. Use .then/.catch, or…
  • async/await + try/catch — asynchronous code that reads top to bottom.
  • const res = await fetch(url) → check res.ok → await res.json().
  • POST: method, headers: {"Content-Type": "application/json"}, body: JSON.stringify(data).
  • Use Promise.all for independent requests.

What is printed, in order? console.log("A"); setTimeout(() => console.log("B"), 0); console.log("C");

  • A B C
  • B A C
  • C B A
  • A C B

The timer callback waits until the current script finishes, even with 0 ms. So A, then C, then B.

Which are the three states of a Promise?

  • start, run, stop
  • pending, fulfilled, rejected
  • open, sent, closed
  • waiting, true, false

A Promise starts pending and settles as either fulfilled (with a value) or rejected (with an error).

The server replies with status 404. What does await fetch(url) do?

  • It resolves normally; you must check response.ok to notice the 404.
  • It throws an error automatically.
  • It retries until it gets 200.
  • It returns undefined.

fetch only rejects on network failure. HTTP error codes still produce a response, so check response.ok or response.status.

Why do we write await response.json() with await?

  • Because JSON is always slow to type.
  • To convert the object into text.
  • Because reading and parsing the body also returns a Promise.
  • It is optional and does nothing.

The body may still be arriving over the network, so .json() returns a Promise of the parsed data.

When sending JSON with fetch, which pair is required?

  • method: "GET" and body: data
  • mode: "json" and body: data
  • type: "object" and data: obj
  • headers: {"Content-Type": "application/json"} and body: JSON.stringify(data)

The header tells the server the format; the body must be the object converted to JSON text.

You need a student's profile and their grades, and neither request depends on the other. What is the faster approach?

  • Await the profile, then await the grades.
  • Start both and wait with Promise.all.
  • Use a while loop until both arrive.
  • Use setTimeout for each one.

Promise.all runs independent requests at the same time, so the total wait is about the time of the slowest one.
