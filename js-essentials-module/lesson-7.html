One click, start to finish

What happens when a user types a name and presses Add?

  1. Event — the browser fires a submit event; your listener runs (Lesson 4).
  2. Request — your code calls fetch("…/api/students", { method: "POST", body: JSON.stringify(data) }) (Lesson 5).
  3. Route — Express matches POST /api/students; express.json() fills req.body (Lesson 6).
  4. Logic — the route validates the data and saves it (in an array today; in a database in real life).
  5. Response — the server answers 201 Created with the new record as JSON.
  6. Update — the front end reads await res.json() and re-renders the list (Lessons 3–4).

7.3 CORS: the error everyone meets

An origin is the combination of protocol, host and port: http://localhost:5500 and http://localhost:3000 are different origins, even on the same computer.

For security, browsers follow the same-origin policy: a page's JavaScript may send a request to another origin, but the browser will not let the page read the answer unless that server says it is allowed. The server says so with a response header: Access-Control-Allow-Origin. This system is called CORS — Cross-Origin Resource Sharing.

Everyday analogy

You (the page from origin 5500) send a letter to another office (the API on 3000). The guard at your building (the browser) opens the reply first. If the reply does not carry the other office's stamp saying "OK to share with 5500", the guard throws it away — even though the other office did answer.

Run the box below. The page pretends to be at http://localhost:5500 and calls an API at http://localhost:3000 that has not enabled CORS. Watch the console.

Press Call the API. Notice two things in the console: the server did receive the request and answer 200, but the browser blocked the page from reading it. Now uncomment api.use(cors());, press ▶ Run, and call it again.

A classmate gets a CORS error and tries to fix it by changing the fetch() code in the front end. Will that work? Which side must change?

No. CORS permission is granted by the server — the one receiving the request — by sending the Access-Control-Allow-Origin header (in Express, app.use(cors())). The front end cannot give itself permission; otherwise the protection would be meaningless. The other fix is option A from 7.2: serve the page and API from the same origin.

In production

cors() with no options allows every website. For a real system, list only your own front end: app.use(cors({ origin: "https://yourname.github.io" })).

7.6 REST or GraphQL?

REST is not the only way to connect a front end to a back end. GraphQL (created at Facebook) exposes one endpoint, and the client sends a query describing exactly which fields it wants.

RESTGraphQL
Request
Endpointsmany (one per resource)one
Data returnedfixed by the server — sometimes too much or too littleexactly the fields the client asked for
Strengthssimple, cacheable, every tool supports itflexible for complex screens and mobile apps with limited data
Costsseveral requests for related datamore setup; harder to cache; needs a schema
A mobile app's home screen needs a user's name, their last 3 orders, and each order's status — nothing else. Data is expensive for its users. Which style fits better, and why?

GraphQL fits well: one request can fetch exactly those fields, with no extra data and no chain of follow-up requests. For a small app with simple screens, REST would still be perfectly reasonable — and simpler to build. "It depends on the use case" is the honest answer, as long as you can explain the trade-off.

7.7 Debugging integration problems

When "it doesn't work," find which tier is failing. On a real computer, check three places: the browser Console, the browser Network tab (Developer Tools, F12), and the terminal where the server runs.

Summary

  • Integration loop: event → fetch → route → logic/database → JSON response → re-render.
  • Serve the page from Express (same origin, relative URLs) or run them separately (needs CORS).
  • CORS is enforced by the browser and granted by the server with Access-Control-Allow-Origin.
  • The server is the source of truth and must validate everything.
  • React does the same integration with useState + useEffect.
  • REST: many endpoints, fixed shapes. GraphQL: one endpoint, client chooses the fields.

Which pair of URLs has different origins?

  • http://localhost:3000/a and http://localhost:3000/b
  • http://localhost:5500 and http://localhost:3000
  • https://psu.edu/x and https://psu.edu/y
  • Both URLs in option A are the same page.

An origin is protocol + host + port. Different ports mean different origins.

Your page on port 5500 calls your API on port 3000 and gets a CORS error. Where is the correct fix?

  • In the front end: add mode: "cors" to fetch.
  • In the browser settings.
  • In the HTML <head>.
  • In the server: send Access-Control-Allow-Origin, e.g., app.use(cors()).

Only the server being called can grant cross-origin access.

The front end already uses a dropdown limited to "2A" and "2B". Why should the server still validate section?

  • Because requests can be sent without your page (e.g., curl or Postman), so the server cannot trust the client.
  • Because dropdowns are slow.
  • It should not; validating twice is wrong.
  • Because JSON cannot store strings.

Client-side checks are for convenience. Server-side checks are for correctness and security.

You see SyntaxError: Unexpected token '<' after await res.json(). What is the most likely cause?

  • The JSON has a missing comma in your front-end code.
  • The server is not running.
  • The server answered with HTML (such as a 404 page) instead of JSON.
  • CORS is blocking the request.

A < at the start means HTML. Check res.ok and the URL.

If Express serves the front-end files with express.static("public"), how should the page call the API?

  • With a full URL to a different port.
  • With a relative URL like fetch("/api/students"), since page and API share one origin.
  • It cannot call the API.
  • Only with GraphQL.

Same server, same origin: relative URLs work and CORS is not needed.

What is a key difference between REST and GraphQL?

  • REST uses JSON; GraphQL cannot.
  • GraphQL only works with React.
  • REST cannot be used from JavaScript.
  • GraphQL uses one endpoint where the client specifies exactly which fields it needs; REST uses many endpoints with server-defined responses.

That flexibility is GraphQL's main strength; REST's main strength is simplicity.
